## 构建和检查

本机已经找到 Keil 工具链 `D:\Keil`。独立构建脚本不调用烧录器、不打开 IDE，也不改写仓库原有编译产物：

```powershell
python tools/build_firmware.py --keil D:\Keil
python tests/run_host_tests.py --gcc D:\Dev-Cpp\MinGW64\bin\gcc.exe
```

生成文件在 `.build/firmware/`：`ElcCarApp.hex`、`ElcCarApp.axf`、`build.log`、`firmware.map` 和调用栈报告。原 Keil 工程也已加入新增源文件，栈由 1KB 调整为 4KB，CubeMX 的栈配置同步修改。

TIM1 由 `Control_StartTimer()` 在独立模块中配置，不使用输出引脚；CubeMX 中不要再把 TIM1 分配给其他功能。TIM2/TIM4 编码器和 TIM3 PWM 的 PCB 引脚保持原分配。CubeMX 重新生成后仍需检查业务模块编译列表与 TIM1 中断入口。

主机测试编译并执行实际的 C 算法、实验状态机和控制引擎，HAL/寄存器为模拟对象；它不能证明实际接线、控制执行时间或电机动态正确。

## 选择模式

- **正常模式**：不按 Start/PB14 上电，保留视觉流程和 PB15 状态切换。
- **调参模式**：按住 Start/PB14 上电或复位，启动时连续两次读到低电平后锁定；进入后可松开。调参模式不初始化 OLED/IMU 业务，也不运行路线状态机。
- 模式直到复位才改变；普通串口数据不能切换模式或直接开动电机。
- 调参时 PB15 为本地停车键，10ms 控制任务会检查它。按键停车、STOP、完成或故障后，下一次实验必须重新 ARM。

若 PCB 上 Start 键的实际连接与项目 PB14 定义不一致，需先核对原理图再使用该入口。当前没有向实板下载此固件。

## USART1 换接

先停止小车并断电，再断开视觉模块，使用 3.3V TTL USB 转串口连接原视觉串口：

| USB 转串口 | MCU 信号 |
| --- | --- |
| RXD | PA9 / USART1_TX |
| TXD | PA10 / USART1_RX |
| GND | GND |

这是信号关系，不是 PCB 插座针序。电源脚按原理图和板卡供电方式确定。视觉模块与 USB 转串口的 TX 不能同时并接到 PA10。当前方案不支持视觉识别与电脑调参同时在线。

## 首次实板检查

先架空驱动轮。进入调参模式后应收到 `READY ELC_AUTOTUNE_V1`，串口参数为 115200/8N1。连接和查询不会驱动电机：

```text
HELLO
VIEW
STATUS
STOP
```

先用 VIEW 检查手动向车体前进方向转动每个轮子时的计数正负。随后 ARM 的两个符号应使归一化后的前进计数都为正。符号不能凭示例猜测；正常模式可通过 `Core/Inc/control.h` 中的 `CAR_ENCODER_SIGN_LEFT/RIGHT` 设置，调参模式的 ARM 会覆盖本次会话的符号，不写 Flash。

速度单位暂为**编码器计数/10ms，不是 RPM**。需要实测每轮有效计数、减速比和编码器倍率后再统一为物理速度。

## 固定参数实车实验

主机需要 pyserial。该脚本会真实驱动电机，只有明确提供端口、两个符号、左右增益、速度峰值和 PWM 上限才会运行。

```powershell
python tools/autotune/bench.py --help
```

确认接线、方向和合理的初始输出后，命令形式如下；各值均需替换为实际确认值，示例占位符不能直接执行：

```text
python tools/autotune/bench.py --port <COM号> --sign-left <1或-1> --sign-right <1或-1> --kp-left <值> --ki-left <值> --kp-right <值> --ki-right <值> --peak <计数每10ms> --pwm-limit <整数>
```

脚本会握手、STOP、等待编码器静止判定、ARM、提交参数、核对实际生效 ACK、自动心跳、导出、校验和评分；结束后确认驱动取消，并等待编码器静止判定。日志在 `tools/autotune/runs/时间戳/`，包含请求、原始 CSV、串口收发及成功/失败 JSON。

评分取左右轮中较差的一侧，使用跟踪误差、阶跃超调/欠调、收敛情况、饱和与输出变化。它是首版实验评价规则，尚未用真实电机的噪声与负载校准，不能把“有效数据”解释成“性能达标”。静止标志仅来自编码器，在传感器断线时不能证明车轮物理静止。

协议、边界及保护见 [调参协议](docs/调参协议.md)。整体分析与后续路线见 [接入前分析](docs/自动调参接入前分析.md)。

## 2026-10-16 第二轮迭代

- ARM 前须连续 300ms 原始计数为零；授权 5 秒有效，超时后不能启动；运行中禁止修改编码器方向。
- 新增 INFO 指令与构建内容指纹，自动搜索要求明确的 16 位固件指纹；未使用独立脚本构建的 unidentified 固件只能用于手工检查。
- 固件/算法身份在实验组之间保持一致；每次实验使用独立请求编号。
- 新入口 tools/autotune/tune.py 支持候选文件或 --codex，并提供 --simulate 模式。
- 默认每组重复三次：基准 → 候选 → 基准复测 → 候选保留确认；确认失败则回退并复测。基准漂移过大时停止。
- 候选单项最多变化 20%，拒绝非有限值、布尔冒充参数、重复候选和舍入后无变化。任一车轮的恶化不能被另一车轮平均掩盖。
- 发生硬件/通信故障时只停车、保存失败并结束搜索，不自动重新启动一次回退实验。
- 参数建议期间串口已经关闭、实验已经取消；Windows CLI 子进程使用独立 Job Object 限时清理，不按进程名杀其他会话。

完全离线检查应组合使用 --simulate 与 --candidate-file；--simulate --codex 仍会调用模型服务，但不会连接串口。两个选项都需要明确初始左右增益、方向、peak 和 pwm-limit。候选 JSON 的字段见 tools/autotune/candidate.schema.json。

真实串口模式需要 --port，不能与 --simulate 同时使用。独立构建产生的 INFO 指纹会随源码、工程配置、构建脚本和编译器版本变化。旧固件没有 INFO 时需先更新固件；不能跳过握手直接运行。

CLI 结构化输出及非交互参数依据 [OpenAI 官方文档](https://learn.chatgpt.com/docs/non-interactive-mode) 和本机 exec --help 核对。模型本身不管理串口，最终是否接受参数由本地主机校验与实际测量决定。
